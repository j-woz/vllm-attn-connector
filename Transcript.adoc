== Exchange 2: How the probe connects to vLLM

[quote,user]
____
how does it connect to vllm. do you need the vllm source
____

=== The connection mechanism

Entirely through vLLM's public backend registry. The sequence in `install()`:

. Import `register_backend` / `AttentionBackendEnum` from
  `vllm.v1.attention.backends.registry` (`probe.py:121`).
. Resolve the live backend class for the requested enum member -- default
  `FLASH_ATTN` -- and take its impl via `get_impl_cls()` (`probe.py:134-139`).
. Build two subclasses at runtime: `_ProbedImpl`, whose `forward` calls
  `_capture(...)` then delegates to `super().forward(...)`; and `_ProbedBackend`,
  which returns `_ProbedImpl` from `get_impl_cls()` (`probe.py:141-153`).
. Rewrite `__name__` / `__qualname__` / `__module__` on both and inject them into
  the module's `globals()` (`probe.py:155-164`), then call `register_backend`.
. Captured decode queries land in the module-level `REGISTRY`, read later by the
  connector half.

Two design constraints were surfaced from the source comments:

Timing:: `install()` must run before engine construction, because
`_cached_get_attn_backend` is `@cache`-decorated and resolves the backend class
exactly once.

Why the impl, not a module hook:: `Attention.forward` is traced through by
`torch.compile`; only the custom op `unified_attention_with_output` survives as a
runtime node, and it dispatches `self.impl.forward(...)` dynamically. Overriding the
impl therefore still fires under CUDA graphs, where an `nn.Module` forward hook
would not.

=== Do you need the source?

No -- but vLLM must be *installed*, and it was not:

[source]
----
ModuleNotFoundError: No module named 'vllm'
----

`pyproject.toml:10` is explicit: `dependencies = []  # vllm and flowcept provided by
the host environment`. Every vLLM import in `probe.py` is wrapped in
`try/except ImportError` with a `logger.warning` and a `return False`, so `install()`
degrades quietly on a machine without it.

[IMPORTANT]
.Interpretive note
====
The distinction drawn here -- *not needing the source* versus *needing the package* --
is the one that actually matters for this codebase, and it is load-bearing for
everything that follows. The probe patches nothing and forks no kernel, but it is
tightly coupled to vLLM's internal *layout*: module paths, enum members, a method
signature, and one platform quirk. That coupling is invisible to a dependency
resolver and therefore invisible to CI. It only shows up when a vLLM upgrade moves
something.

This is precisely the gap the user closes in the next turn.

== Exchange 4: The export path to Flowcept

[quote,user]
____
how does the connector export data from vllm to flowcept. flowcept is in deps
____

Exactly one Flowcept import exists in the whole of `src/` (`connector.py:431`). The
full chain:

.Stage 1 -- Setup, `_WorkerSide.__init__` (`connector.py:431-434`)
[source,python]
----
from flowcept.flowceptor.adapters.vllm.vllm_interceptor import VLLMInterceptor
self._interceptor = VLLMInterceptor.get_instance()
self._interceptor.start(bundle_exec_id=workflow_id)
----

Singleton, started once per worker process. `start()` brings up the MQ DAO;
`send_workflow_message` raises if it was never called
(`base_interceptor.py:146-148`).

.Stage 2 -- Run-level record (`connector.py:513`)
Rank 0 only. `send_model_workflow(workflow_id, conf, parent_workflow_id=...)` builds
a `WorkflowObject` carrying the model config -- crucially the tokenizer identity,
without which the `prompt_token_ids` on every later task cannot be decoded.
`send_workflow_message` dedupes on `workflow_id` via `_saved_workflows`, so
re-registration is a silent no-op.

.Stage 3 -- Per-request record, `emit_finished` → `_emit` (`connector.py:740-851`)
Driven by vLLM's `KVConnector` request-finished hook. Per finished request: pop the
`_RequestState`, `st.event.synchronize()`, then emit *one task per KV-cache group*,
keyed `f"{req_id}:g{group.gid}"`.

The GPU→host conversion happens inline -- every tensor goes
`.double().round(decimals=FLOAT_DECIMALS).tolist()`. Nothing tensor-shaped crosses
into Flowcept.

The payload splits in two:

`series`:: numeric arrays. Flat per-token (`attn_sum`, `attn_peak`, length `n_keys`)
and matrices (`topk_pos`, `topk_head`, the `AGG_FIELDS`, `topk_residual`,
`segments`), shaped `[G, k]` for `G` decode steps.

`metadata`:: everything needed to interpret those arrays without guessing --
`matrix_shape`, `matrix_fields`, `head_code`, `no_entry_sentinel`,
`segments_layout`, per-head/per-layer statistics, and provenance such as `restarts`
and `decode_steps_dropped`.

.Stage 4 -- Adapter (`vllm_interceptor.py:113-194`)
`capture_request` → `callback` → `prepare_task_msg` → `intercept(task_msg.to_dict())`.

`prepare_task_msg` distinguishes flat series from matrices by peeking at `v[0]`. Only
flat series must agree on length, and that agreed length becomes
`num_computed_tokens`; matrices are checked only for raggedness.

.Stage 5 -- Out (`base_interceptor.py:184-186`)
[source,python]
----
def intercept(self, obj_msg): self._mq_dao.buffer.append(obj_msg)
----

Fire-and-forget. Flowcept's flush thread drains the buffer onward.
`connector.py:861` calls `self._interceptor.stop()`, which is what guarantees the
tail is flushed.

=== Two observations raised

TP guard is tautological:: `connector.py:747` reads
`if self._tp_rank == 0 or self._tp_size > 1:`, but `_emit` itself returns at line 756
when `self._tp_rank != 0`. Non-zero ranks enter `_emit`, run `st.event.synchronize()`
and compute `n_keys`, then bail. Net behaviour is correct -- only rank 0 emits -- but
the guard *reads* as though non-rank-0 emission were intended. It could be
`if self._tp_rank == 0:` unless the sync on other ranks is deliberate.

Interceptor started on every rank:: `connector.py:434` runs on all ranks, including
those that never emit. Each spins up an MQ connection that sends nothing. Harmless,
but it explains idle MQ clients scaling with TP degree.

[NOTE]
.Interpretive note
====
Both observations are the same species: *behaviour is right, intent is unreadable*.
Neither is a bug and neither was presented as one. The value is in flagging places
where a future reader must reverse-engineer whether something is load-bearing --
the same failure mode as the stale comment in Exchange 3, arrived at from a
different direction.

Note also the deliberate type isolation across the boundary: the connector imports
no Flowcept dataclass and Flowcept imports no torch. The two halves share only
primitives. This is what makes the Paccmann pivot in Exchange 8 tractable at all.
====

== Exchange 5: What type crosses the boundary

[quote,user]
____
so what is the type of object passed from the connector to flowcept
____

[NOTE]
The user ran `/effort` immediately before this turn, setting effort to *medium*.
The answers from here on are correspondingly tighter.

The answer is that the type changes three times, and at the boundary itself there is
no object -- only kwargs.

.At the call boundary (`connector.py:813`)
[cols="1,2",options="header"]
|===
| Argument | Type

| `workflow_id`, `request_id`, `activity` | `str`
| `series` | `dict[str, list]` -- values are `list[float]` (flat, per prompt token) or
  `list[list[float\|int]]` (matrices, `[G, k]`)
| `prompt_token_ids` | `list[int]`
| `started_at` | `float`
| `metadata` | `dict[str, Any]`
|===

.Inside the adapter
`prepare_task_msg` packs those into a `TaskObject`
(`flowcept/commons/flowcept_dataclasses/task_object.py:18`): `task_id = request_id`,
`activity_id`/`subtype = activity`, `status = Status.FINISHED`, `used = {...}`,
`generated = series`, `custom_metadata = metadata`. The run-level call builds a
`WorkflowObject` instead.

.On the wire
`callback` ends with `self.intercept(task_msg.to_dict())`. `to_dict`
(`task_object.py:220`) walks `__dict__`, drops `None` fields, unwraps enums to
`.value`. What reaches the buffer is a JSON-serialisable `dict`.

*Primitives → `TaskObject` → `dict`.*

== Exchange 6: Is `TaskObject` the storage format?

[quote,user]
____
so flowcept stores TaskObjects?
____

No. `TaskObject` never leaves the producer process -- it is a transient builder.

. `prepare_task_msg` constructs it.
. `callback` calls `to_dict()` and appends the *dict* (`base_interceptor.py:186`).
  The `TaskObject` is garbage after that line.
. The dict is serialised onto the MQ (Redis/Kafka), crossing a process boundary.
. `DocumentInserter` receives it still as a dict and calls
  `TaskObject.enrich_task_dict(message)` (`document_inserter.py:149`) -- a static
  helper that mutates the *dict*, not a rehydration.
. It hands the list to `dao.insert_and_update_many_tasks(buffer, TaskObject.task_id_field())`
  (`document_inserter.py:111`), signature `(doc_list: List[Dict], indexing_key=None)`
  (`mongodb_dao.py:265`).

`TaskObject` survives in the consumer only as a source of field-name constants:
`task_id_field()` and `workflow_id_field()` build the indexes
(`mongodb_dao.py:98-101`), with `task_id` *unique* on the tasks collection.

[IMPORTANT]
.Interpretive note
====
The unique index is the detail that repays the whole excavation. `_emit` keys tasks
as `f"{req_id}:g{group.gid}"` (`connector.py:815`). That `:g{gid}` suffix is not
cosmetic -- it is what prevents multiple KV-cache groups from colliding on the unique
`task_id` index and silently overwriting one another.

A reader who assumed the suffix was for human legibility, and dropped it during a
refactor, would lose all but one group's data per request with no error raised.
Chasing the dataclass question to the actual storage layer is what exposed the
constraint.
====

== Exchange 7: Document granularity

[quote,user]
____
so there is 1 mongodb document per LLM inference?
____

Per finished request *per KV-cache group* -- which for most models is 1.

`_emit` loops `for gi, group in enumerate(self._scored)`, calling `capture_request`
once per iteration (`connector.py:813`). `self._scored` is built in
`register_kv_caches` from `kv_cache_config.kv_cache_groups`, retaining only groups
with at least one layer whose layout resolved.

* Plain full-attention model → one group → one document.
* Hybrid / sliding-window model (interleaved global + local layers) → several groups
  → one document per group per request.

.What does *not* multiply the count
Decode steps:: All `G` steps are packed into matrices inside the single document.
One doc per request, not per token.
Tensor parallelism:: Only `tp_rank == 0` emits (`connector.py:756`).
Layers:: Aggregated over `(layer, head)` within the group before emission.

.Zero documents
`connector.py:743-745` -- state never created, `colsum is None`, or `steps == 0`
(e.g. a request that finished without a captured decode step). The `req_id` still
enters `_emitted`, so the scheduler side treats it as handled either way.

Separately: one `WorkflowObject` document per run.

== Exchange 8: A Paccmann MCA analogue

[quote,user]
____
what is the equivalent in the Paccmann source that we could attach to with the
connector with a few code changes. can we attach the connector to the MCA model
layers and produce something similar at inference time?
____

Answer: yes, and it is substantially *easier* than the vLLM case, because the hard
half of the existing design does not apply.

=== Why the difficulty collapses

The vLLM work needed two extension points because decode queries are transient: they
never enter the KV cache, `torch.compile` erases `Attention.forward`, and CUDA graphs
defeat module hooks. Hence the backend-impl override plus `layout.py` / `kernels.py`
to re-derive scores against cached K.

MCA has none of this. It is a single-pass encoder-regressor, eager mode, no KV cache,
no autoregression. *The attention weights are already materialised and already
returned* -- and then discarded.

=== Attach points, ranked

[[attach-1]]
==== 1. `prediction_dict` -- `paccmann_predictor/models/paccmann.py:271-283`

[source,python]
----
prediction_dict.update({
    'gene_attention': gene_alphas,                   # [bs, 2128]
    'smiles_attention': smiles_attention_weights,    # [bs, 560]
    'IC50': predictions, ...
})
----

Gated on `if not self.training`, so live exactly on the inference path. The built-in
analogue of `REGISTRY`.

Caveat: `smiles_attention_weights` is `torch.mean(...)` over the head axis
(`paccmann.py:273-279`), which *destroys* the per-head structure the vLLM payload
preserves (`topk_head`, `head_code`, `head_entropy`). The raw `smiles_alphas` list --
16 tensors, `multiheads=[4,4,4,4]` → 4 layers × 4 heads -- exists at
`paccmann.py:253` and is thrown away. Retaining it is a one-line change.

[[attach-2]]
==== 2. `ContextAttentionLayer.forward` -- `paccmann_predictor/utils/layers.py:210`

The true probe analogue. `alphas` is computed at line 232, shape `[bs, T]`. With no
`torch.compile` in the path, a plain forward hook works -- the very thing that would
not work in vLLM:

[source,python]
----
for name, m in model.named_modules():
    if isinstance(m, ContextAttentionLayer):
        m.register_forward_hook(lambda mod, inp, out, n=name: REGISTRY.put(n, out[1]))
----

Zero edits to Paccmann source, matching the project's existing "no vLLM source is
patched" stance.

[[attach-3]]
==== 3. The inference loop -- `test_paccmann.py:170-176`

[source,python]
----
y_hat, pred_dict = model(torch.squeeze(smiles.to(device)), gep.to(device))
predictions.append(y_hat)
----

`pred_dict` is bound and never used. The attention data is computed on every
inference batch and dropped on the floor. This is where `emit_finished` belongs.

=== Schema mapping

[cols="2,3",options="header"]
|===
| vLLM connector | MCA equivalent

| request-finished hook | end of each batch, `test_paccmann.py:170`
| one doc per `{req_id}:g{gid}` | one doc per sample; `:g0` SMILES, `:g1` gene
| `prompt_token_ids` | the `smiles` row of token ids, decoded via `smiles_language`
| workflow `conf` with tokenizer identity | `params` with `smiles_language_filepath`,
  `smiles_vocabulary_size`, `modelpath`
| `attn_sum` / `attn_peak` over (layer, head) | sum / max of `alphas` over the 16 heads,
  per SMILES token
| `head_code = layer * H + head` | `ind = multiheads[0] * layer + head`, already
  computed at `paccmann.py:248`
| `matrix_shape [G, k]` | *G = 1* -- no decode loop
|===

=== Stated limitations

Two were raised explicitly rather than glossed:

No temporal axis:: The vLLM records capture how attention *evolves across
generation*. MCA yields one static distribution per prediction. `topk_residual`,
`decode_steps_dropped`, `wins_first_step` vs `wins_later_steps`, and the
preemption/restart logic have no counterpart.

Different quantity:: MCA attention is additive / Bahdanau-style --
`tanh(W_r·ref + W_c·ctx) → Linear → softmax` (`layers.py:199-233`) -- not
`softmax(qKᵀ/√d)`. The `metric_reference` string would have to change; the numbers
are not the same measurement.

=== Scope estimate

Reusable as-is:: `VLLMInterceptor`. Its own docstring states "the adapter imposes no
meaning on the series", and `activity` exists so that multiple connectors can share
one store. Only the class name is vLLM-flavoured.

Not reusable:: `probe.py`, `layout.py`, `kernels.py` -- all solve problems MCA does
not have. 560 SMILES tokens × 16 heads is trivial to move; full vectors can be
emitted and `_segment_plan` / top-k skipped. Genes at 2128 are the only place top-k
might earn its keep.

Estimated: one hook registration, one emit function (~60 lines), two call sites in
`test_paccmann.py`, optionally one line in `paccmann.py`.

[TIP]
.Interpretive note
====
The pivot here is the session's real payoff, and it only works *because* of
Exchanges 4-7. Knowing that the boundary carries primitives -- not torch tensors, not
a vLLM-specific dataclass -- is what makes "point it at a completely different model"
a sixty-line proposition rather than a rewrite.

Note too that the difficulty inverts. In vLLM the sensor is hard (transient queries,
compiled graphs) and the schema is natural. In MCA the sensor is trivial (the weights
are handed to you) but the schema is a poor fit: the `[G, k]` matrices that carry the
design's richest signal collapse to `G = 1`.

The honest framing offered was that this yields *which SMILES tokens and which genes
mattered for this prediction* -- genuinely useful provenance -- but not the temporal
attention dynamics the vLLM path was built to capture. Same pipeline, same store,
materially different scientific claim.
====

== Addendum: the Paccmann analogue, implemented

_Added 2026-09-17 by Rajeev Jain. The session above scoped this in Exchange 8;
this records what was built and what it cost. Full write-up in
`docs/cancer-study.md`._

Exchange 8 estimated "one hook registration, one emit function (~60 lines), two
call sites in `test_paccmann.py`, optionally one line in `paccmann.py`". That
was close. The emit path came to about that size; what the estimate did not
carry was the state of the models themselves.

=== What was built

Five modules over one shared base, in `src/vllm_attn_connector/`:

`drp_emit.py`:: Reduces per-head attention to `attn_sum` / `attn_peak` /
  `attn_argmax_head` -- the vLLM payload's own field names, so one consumer
  reads both producers -- and emits through `VLLMInterceptor`. Imports no
  framework, so it is testable in a base install.

`drp_capture.py`:: `AttentionCapture`, owning everything downstream of
  "attention is in hand". A model supplies three constants and a `collect()`.

`drp_paccmann.py`:: Forward hooks on `ContextAttentionLayer`. Exchange 8 named
  this as attach point 2 and it is the right one: hooking the layer catches all
  16 per-head vectors *before* `paccmann.py:273-279` averages them away, so
  `attn_peak` and `attn_argmax_head` are real rather than reconstructed from a
  mean.

`drp_hidra.py`:: A second Keras model over the same trained weights. Every
  HiDRA attention layer is explicitly `name=`d, so the pathway distribution
  comes out with no edit and no retraining.

`drp_chains.py`:: Reads captured attention back out of MongoDB and builds
  OPAL-format evaluation chains from it.

Neither model repository is patched, matching the project's stance on vLLM.

=== What the estimate did not include

Neither model ran on a current environment. Four defects in Paccmann, two of
them silent:

. `np.float` removed in numpy 1.24; pytoda 1.1 raises on `device=`; predictions
  stack to `(N,1)` where `pearsonr` wants 1-D.
. The curated SMILES pickle is a bare `SMILESLanguage`; pytoda 1.1 wants a
  `SMILESTokenizer`. Fixing it exposed that pytoda takes the augment flag from
  the *language object*, so validation was being silently augmented -- val MSE
  0.0188 -> 0.0143.
. *Gene expression arrived as all zeros.* The v0.1.0 omics loader expects a
  three-row header; `drp_data_v0.2.0` has one. The 2128-gene lookup matched
  nothing and the model trained on zeros. Nothing raised. The only tell was val
  R2 0.37 against test R2 -3.19. After the fix, test PCC 0.687 -> *0.787*.
. *Inference was not reproducible.* pytoda assigns indices to six unseen SMILES
  tokens from a set difference, whose iteration order varies per process, and
  those indices hit a trained embedding. Three runs of one unchanged command
  gave test PCC *0.787, 0.491, 0.787*.

Fixes are on `github.com/rajeeja/Paccmann_MCA`, branch `rajeeja/py313-fixes`.
Upstream `JDACS4C-IMPROVE/Paccmann_MCA` has been inactive since 2024-09.

=== The measurement, and its limits

Verified against real checkpoints: 16 heads captured as the architecture
implies, every distribution a real softmax, heads disagreeing (so the per-head
structure survived), and predictions bit-identical with capture installed --
provenance must observe, not perturb.

Exchange 8's two stated limitations both held. There is no temporal axis:
`decode_steps_recorded` is 1, and everything step-indexed in the vLLM payload
has no counterpart. And the quantity differs -- Paccmann's attention is
additive/Bahdanau, HiDRA's a learned softmax gate, neither
`softmax(qK^T/sqrt d)` -- so each record carries a `metric_reference` and the
numbers are not pooled across producers.

=== One finding worth keeping

On the gene axis, *PARN is the top-attended gene on all 371 cell lines*, at
0.9988 of the weight. Second place is three orders of magnitude down.

That is the drug-response analogue of the attention sink this connector already
excludes at position 0, and it was discovered in captured output rather than
assumed. It is also why an attribution claim naming PARN is vacuous, and why
the benchmark's attention task carries a distractor.
